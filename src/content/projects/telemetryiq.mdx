## Problem and constraints

<Confirm>Problem statement pulled from the project README. Check it matches the hackathon brief.</Confirm>

The README describes a platform that correlates code deployments and configuration changes with performance drops, and traces possible failure paths to estimate downstream risk, affected users and financial exposure.

BeachHack H4C was a 36-hour flagship hackathon at CCE. The team was about four people, and I built all the ML: two models, one for anomaly detection and one for the other functions. Both were trained on a large mock dataset.

## Key decisions

What we built and why it fits the problem.

### 1. Two models on the same features

`/ml/scan` computes 15 features (CPU, memory, request and cost statistics) from recent metrics, then runs an Isolation Forest for an anomaly score and a Random Forest for a prediction with class probabilities. Splitting the work this way gives one model dedicated to anomaly detection and one for everything else.

### 2. Correlate anomalies with change events

`/ingest/change` records deployments and config changes, and the correlation engine compares baseline and current features around the latest change to produce a confidence and a delay in minutes.

### 3. Mock services to test against

`mock-services` exposes Prometheus gauges and posts metrics to the backend, with three scenarios: `memory_leak`, `bad_deploy` and `good_spike`.

## MLOps specifics

What the repo shows:

- A Docker Compose stack of MongoDB, the FastAPI backend, Prometheus (v2.54.1), Grafana (11.2.0), the mock services and the Next.js frontend.
- Prometheus scrapes the mock services' exporter every 2 seconds. Grafana has a provisioned Prometheus datasource and a custom `grafana.ini`.
- Models are pre-trained `.pkl` files loaded with joblib when the backend starts.
- Metric and change ingestion, an on-demand `/ml/scan` and a change history view in the dashboard.

What the repo does not show: Grafana dashboards (only the datasource is provisioned), alert webhooks, automatic scaling or cost policies, CI configuration, tests, or the training code and data for the models.

## Limits and what is next

- Both models were trained on a large mock dataset, not real production telemetry.
- Nothing broke during the build.

Next steps are improvements: moving to real data, adding a proper evaluation, and building a training pipeline.
